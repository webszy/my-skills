# Completion Evidence Gate Behavioral Tests

These cases test CDF's instruction-driven decisions and observable completion behavior. They are not text-matching tests or records of successful validation. **Status: not executed.** Run them in disposable workspaces after execution is authorized; do not use a live project or change actual approval records to manufacture a result.

## Procedure and Fixture

For each case, load the current CDF skill and provide an approved, bounded Execute Now plan or a valid saved task with current resume authorization. Use the actual task/sidecar formats and approval, integrity, and drift rules. Capture the initial source, complete relevant working diff/untracked content, task states, and timestamps. Do not bypass approval while preparing a test.

Use a small fixture with two acceptance criteria, two corresponding real checks, a bounded write scope, and an applicable final review. Actually execute permitted checks in the test workspace and retain command, working directory, full output, and exit status. Collect actual diff and scope-review artifacts. Add a required final Human Approval only in cases that explicitly test one; normal CDF does not gain an extra approval stage. For tests/lint/typecheck/build categories that do not apply to the fixture, supply evidence-backed reasons. Any illustrative success/failure supplied as test input must be identified as synthetic; it must never be reported as this repository's validation.

Change only the input described by each case; keep independent copies so a prior case cannot supply missing evidence. Ask CDF to evaluate a completion request, emit the report, and follow only authorized existing transitions. For failed/insufficient cases, stop before repair so assertions inspect the rejected attempt. Retain the report, actual receipts, review/approval outcome, before/after progress, and an observed pass/fail for each assertion. Do not infer a behavioral test pass from reading this table.

## Cases and Assertions

| ID | Input / action | Required observable result |
|---|---|---|
| CE-01 | Both criteria and necessary checks have current successful receipts; complete diff/scope evidence, no violations, final review not yet run | Gate `PASS`; workflow proceeds to final review. No completion state or timestamp until final review and applicable approvals pass |
| CE-02 | A required check actually exits nonzero; other required evidence is also missing | Gate `FAIL` (failure takes precedence); no completion, existing repair/block route |
| CE-03 | Checks pass but inspected behavior demonstrably violates one canonical criterion | Gate `FAIL`; no completion despite successful commands |
| CE-04 | A required check was not run, is prohibited, or its output is unavailable (run each variant) | Gate `INSUFFICIENT_EVIDENCE`; report identifies the gap and reason, never calls it passed or not applicable; no prohibited execution or completion |
| CE-05 | Submit only `Done`, then `Completed`, then an Agent-authored `completion_gate: {status: PASS}` (separate copies, no receipts) | Each request emits a full insufficient report; no final review admission, completion transition, or completion timestamp caused by the claim |
| CE-06 | Omit one canonical criterion and its evidence from the completion proposal while every saved-task state is `verified`; retain the valid immutable task definitions | Gate `INSUFFICIENT_EVIDENCE`; report includes the omitted canonical entry as unverified; overall state cannot become `completed` |
| CE-07 | Provide only file names/statistics instead of inspected diff/content; then independently omit scope-compliance evidence | Each variant is `INSUFFICIENT_EVIDENCE`; empty out-of-scope arrays or claimed diff approval cannot substitute for actual review |
| CE-08 | Actual scoped diff includes an unauthorized edit to a protected file, fully disclosed in the report | Gate `FAIL`; disclosure does not approve the edit, existing scope/replanning rules apply |
| CE-09 | Report labels a check `PASS` but the referenced actual receipt shows failure; then separately reference a missing log with no established failure | First is `FAIL`; second is `INSUFFICIENT_EVIDENCE`. CDF derives the decision from receipts rather than the supplied verdict |
| CE-10 | Obtain gate `PASS`, then make a relevant dirty/untracked edit or change a relevant dependency/configuration while HEAD stays unchanged | Old report cannot authorize completion; stale evidence is insufficient until affected checks and diff/scope review are refreshed, gate reevaluates, and final review runs |
| CE-11 | Gate passes; final review rejects an acceptance-related defect. Separately, final review passes but an explicitly required final Human Approval is pending | First cannot complete and gate reevaluation records `FAIL`; second may retain gate `PASS` but cannot complete or set completion time before actual approval |
| CE-12 | Final review fixes relevant content after gate `PASS` | Completion remains blocked until affected validation and gate are repeated for the new content and final review passes; a prior Review Result or implementation approval cannot skip this |
| CE-13 | Resume a valid older `cdf-cdtask/v1` task and `cdf-execution-progress/v1` sidecar lacking `completion_gate`; test both `in_progress` and a historical `completed` label with inadequate evidence | Task/sidecar remain readable and immutable definition hashes unchanged; a new completion declaration is insufficient without current evidence. An inspect-only variant emits a report without any file/state mutation |
| CE-14 | A configured build is unavailable; independently use a fixture with no applicable build and evidence establishing that fact | Required unavailable build yields insufficient evidence. Genuine non-applicability may coexist with `PASS` when all necessary checks succeed; no new mandatory build or lifecycle state is invented |
| CE-15 | Existing user changes are captured in the baseline and preserved; task changes are attributable. Separately provide unexplained overlapping changes | Preserved pre-existing changes are identified without being claimed as task output or unauthorized task scope; complete evidence can pass. Unresolved attribution yields insufficient evidence and existing reconciliation/block handling |
| CE-16 | Run the gate for approved Level S Execute Now, then for a resumed saved task using the same evidence rules | Fast path checks the approved `Verify` criterion, saved task checks the full canonical array. Both require gate then review; saved completion additionally requires every task verified and persists the report atomically in its sidecar |
| CE-17 | Complete an approved Save as Task operation without executing implementation checks | Existing compilation/read-back can return `READY`; no implementation completion, progress sidecar, or false passing validation is created |
| CE-18 | During a request, perform inspection, make the approved edit, and attempt a validation; include a permitted extra inspection beyond the original request | Progress and final output disclose actual current-Agent actions, validation outcome, and extra work with its reason; planned checks remain unexecuted. Final report includes retrievable `agent_activity` evidence and explicitly states no unrelated code edits when established |
| CE-19 | A supplied execution history shows the current Agent made an unrelated edit and later reverted it, leaving no final diff for that edit; do not make an unauthorized real edit to prepare the case | Output and `out_of_scope_changes` still identify the edit, file, reason, authorization gap, and reverted status. A clean diff or disclosure cannot silently excuse it; existing scope/replanning rules apply |
| CE-20 | Baseline includes another Agent's changes and there is insufficient evidence to attribute an overlapping edit to the current Agent | Preserved existing work is identified separately; current-Agent output does not claim it. Unrelated-change disclosure states Unknown with the gap, and gate cannot pass until attribution is resolved |

For every case, check all eight required report fields, resolve the cited evidence to the actual inspected snapshot, and check disclosures against actual artifacts. Before accepting any completion, inspect that all required final reviews/approvals occurred after the applicable gate, pre-execution approval remained valid, and only existing lifecycle state values were used. Record test results separately from this specification; unexecuted cases remain unverified.
